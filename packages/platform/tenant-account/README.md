# tenant-account

Bills a tenant's buckets to the tenant's own AWS account. AWS has no billing
account you link a resource to: whoever owns the account pays. So instead of
the platform paying and re-billing, the bucket is created **in the client's
account**. The client creates a role that the platform's Crossplane provider
may assume. Each tenant namespace gets a namespaced `ProviderConfig` that
assumes that role. A `Bucket` XR naming that config in
`spec.providerConfigName` composes every managed resource in the client's
account. The platform never becomes the payer of record.

Two outputs from one values file:

- **cluster** (default): one `ProviderConfig` (`aws.m.upbound.io/v1beta1`,
  namespaced) per account, plus the `ValidatingAdmissionPolicy` and binding
  `bucket-client-account`. In the listed namespaces, every Bucket must set
  `spec.providerConfigName` to one of that namespace's configs, so a bucket
  can never fall back to the platform's own account by omission.
- **client**: per account, the CloudFormation template the client deploys.
  It creates the provisioner role and, with `accessRoles`, the permissions
  boundary that caps the access roles the platform may create.

## Usage

```bash
# cluster side
just tenant-accounts accounts.yaml | kubectl apply -f -
kcl run packages/platform/tenant-account -D values=accounts.yaml -q

# client side: hand this to tenant-a's AWS admin
kcl run packages/platform/tenant-account -D values=accounts.yaml -D output=client -D namespace=tenant-a -q > tenant-a.cfn.yaml
aws cloudformation deploy --template-file tenant-a.cfn.yaml --stack-name platform-provisioner --capabilities CAPABILITY_NAMED_IAM
```

- `-D values=`: an explicit path that does not exist fails the render. With
  none, `values.yaml` in the current directory is read if present, otherwise
  the built-in demo renders.
- `-D output=`: `cluster` (default) or `client`.
- `-D namespace=`: client output only; renders just that tenant's template(s).
  Fails if the namespace is not listed, naming the ones that are.

Then, in the tenant namespace:

```yaml
apiVersion: cloud.example.org/v1alpha1
kind: Bucket
metadata: {namespace: tenant-a, name: assets}
spec:
  region: eu-west-1
  providerConfigName: aws                 # created in, and billed to, 444455556666
  # only with accessRoles, and only for spec.access:
  federation:
    awsAccountId: "444455556666"          # the client's account (its IAM OIDC providers)
    awsPermissionsBoundary: arn:aws:iam::444455556666:policy/platform-provisioner-access-boundary
  crossplane:
    compositionSelector: {matchLabels: {provider: aws}}
```

## Inputs

Validated as `lib.Values`.

| key | type | default | meaning |
| --- | --- | --- | --- |
| `platform.roleArn` | string | required | IAM role the Crossplane AWS provider runs as; the only principal a client role trusts. Its partition (`aws`, `aws-us-gov`, `aws-cn`) is used for every ARN rendered |
| `platform.credentials` | ProviderConfig `spec.credentials` | `{source: IRSA}` | how the provider obtains `roleArn`; passed through, typed against the aws family schema (`IRSA`, `PodIdentity`, `WebIdentity`, `Secret`, ...) |
| `platform.roleName` | string | `platform-provisioner` | name of the role each client creates |
| `accounts[].namespace` | string | required | tenant namespace; the ProviderConfig lives there |
| `accounts[].accountId` | string | required | the client's 12-digit account id |
| `accounts[].externalId` | string | required | `sts:ExternalId` the role demands (confused-deputy guard); unique per client, generated by the platform |
| `accounts[].name` | string | `aws` | ProviderConfig name, i.e. the Bucket's `spec.providerConfigName`; a namespace may list several accounts under different names |
| `accounts[].roleName` | string | `platform.roleName` | per-client override |
| `accounts[].accessRoles` | bool | `false` | let the platform create the IAM roles of `spec.access` (see below) |

A duplicate `namespace`/`name` pair, a malformed account id, external id or
role name, a non-role `platform.roleArn`, or an empty `accounts` list fails
the render.

## What the client grants

The role trusts only `platform.roleArn`, with `sts:ExternalId` required.

| policy | actions | resource |
| --- | --- | --- |
| `buckets` | `s3:*Bucket*`, `s3:Get*Configuration`, `s3:Put*Configuration`: create, delete and configure buckets, which covers every companion MR of the aws backend | `arn:aws:s3:::*` |
| `buckets` | `s3:DeleteObject`, `s3:DeleteObjectVersion`, so `forceDestroy` can empty a bucket | `arn:aws:s3:::*/*` |
| `access-roles` (`accessRoles`) | `CreateRole` only with the boundary and boundary tag; `PutRolePolicy` / `DeleteRolePolicy` only on capped roles; update, tag and delete only on roles carrying the boundary tag, which cannot be removed; IAM reads | `arn:aws:iam::<account>:role/<namespace>-*` |

The `AccessBoundary` managed policy (`<roleName>-access-boundary`) is the
ceiling of every access role: S3 object data plus `kms:Decrypt` /
`kms:GenerateDataKey`. It never allows IAM or bucket configuration writes. The
bucket backend scopes each role's inline policy to its one bucket.

Not granted: object reads or writes for the provisioner itself, any IAM
outside the tenant prefix, and permission to change or remove a role's
boundary.

Residual reach worth telling the client:

- `buckets` covers **every** bucket in the account, including
  `PutBucketPolicy`. Point the platform at a dedicated (member) account, not
  one holding unrelated data.
- With `accessRoles`, the platform can mint roles that the trusted CI
  identities may use to read and write S3 object data anywhere in that
  account (inside the boundary).

## Platform-side prerequisites

- The provider's role (`platform.roleArn`) needs `sts:AssumeRole` on
  `arn:aws:iam::*:role/<roleName>`, or on the listed client roles.
- Tenants must not be able to create or edit `ProviderConfig`s in their own
  namespaces (RBAC). Otherwise a tenant could point a config at any account
  the platform role can reach.
- `bucket-client-account` checks Bucket `CREATE` and `UPDATE`. A Bucket that
  already exists in a listed namespace without `providerConfigName` is denied
  on its next update, including Crossplane's own. Set the field first (or
  delete the bucket), then apply the policy.
- `spec.access` in a client account needs the client's IAM OIDC provider for
  each issuer (as on any AWS bucket) and, with `accessRoles`,
  `federation.awsPermissionsBoundary`. Without it, AWS denies `CreateRole` and
  the error shows on the `Role` MR.

## Outputs

- cluster: a YAML stream of `ProviderConfig` objects (label
  `cloud.example.org/aws-account-id`), then one `ValidatingAdmissionPolicy`
  and one `ValidatingAdmissionPolicyBinding` (`admissionregistration.k8s.io/v1`,
  Kubernetes ≥ 1.30). The allowed names are a CEL map literal, so no params
  object is needed. The binding selects namespaces by
  `kubernetes.io/metadata.name`.
- client: one CloudFormation template per account (YAML stream when there
  are several). Outputs: `RoleArn`, plus `AccessBoundaryArn` with
  `accessRoles`.
