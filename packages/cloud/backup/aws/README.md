# backup-aws

AWS Backup backend for the `BackupPlan` XR (`cloud.example.org/v1alpha1`,
Composition `backup-aws`, label `provider: aws`). Typed against the schema
packages [`packages/providers/aws-backup`](../../../providers/aws-backup) and
[`packages/providers/aws-iam`](../../../providers/aws-iam). It protects one EKS
cluster: AWS Backup takes a composite recovery point holding the cluster state
(every Kubernetes object, add-ons, access entries, node groups) plus a nested
recovery point per EBS/EFS/S3 persistent volume. No agent runs in the cluster —
AWS Backup reaches it through an EKS access entry it creates for the role this
plan composes. `function-kcl` runs it from
`oci://docker.io/yurikrupnik/backup-aws`; `function-auto-ready` follows.

## Composed resources

All are namespaced (`*.aws.m.upbound.io`) Crossplane managed resources in the
XR's namespace, on the provider's default ProviderConfig. The regional ones
land in the region parsed from `spec.cluster.id`, since an AWS Backup plan can
only select resources in its own region.

| resource | when | notes |
| --- | --- | --- |
| `Vault` (`vault`) | always | external name pinned to the XR name; `kmsKeyArn` from `encryptionKmsKeyId`; `forceDestroy` never set |
| `Role` (`role`) | always | trusted by `backup.amazonaws.com`; name generated by Crossplane (IAM is global, an XR-derived name would collide across regions and namespaces) |
| `RolePolicyAttachment` (`role-backup`) | always | `AWSBackupServiceRolePolicyForBackup` — EKS cluster state, EBS/EFS volumes and the access entry |
| `RolePolicyAttachment` (`role-restore`) | always | `AWSBackupServiceRolePolicyForRestores`, so the same role can be handed to `aws backup start-restore-job` |
| `Plan` (`managed`) | always | one rule targeting the composed vault (`targetVaultNameSelector.matchControllerRef`) |
| `Selection` (`selection`) | not `paused` | the cluster ARN, run as the composed role, attached to the composed plan |

The name in parentheses is the `krm.kcl.dev/composition-resource-name`
annotation. Policy ARNs follow the cluster ARN's partition (`aws`, `aws-cn`,
`aws-us-gov`).

A custom role rather than the `AWSServiceRoleForBackup` service-linked role:
an EKS backup works by creating an EKS access entry for the role it runs as,
and the service-linked role is not permitted to create one.

## Spec fields read

Full schema: [`../xrd/xrd.yaml`](../xrd/xrd.yaml).

| field | maps to |
| --- | --- |
| `cluster.id` | **required**: the EKS cluster ARN `arn:aws:eks:<region>:<account>:cluster/<name>`; `Selection.resources`, and its region places every regional MR. Anything else fails the render |
| `schedule` | rule `schedule`, rewritten to `cron(m h dom mon dow year)` with `scheduleExpressionTimezone: Etc/UTC` (see below) |
| `retentionDays` | rule `lifecycle.deleteAfter` (default 30) |
| `encryptionKmsKeyId` | `Vault.kmsKeyArn`; must be a KMS key ARN. Unset means the AWS-owned default key |
| `paused` | `true` withdraws the `Selection` (see below) |
| `deletionPolicy` | `Orphan` → `managementPolicies: [Observe, Create, Update, LateInitialize]` on every MR |
| `tags` | `Vault` and `Plan` tags, and rule `recoveryPointTags` on every recovery point |
| `metadata.name` | vault name, plan name, rule name, selection name — so it must be 2-50 of `[A-Za-z0-9_-]` (the vault's limit; a Kubernetes name may carry dots), else the render fails |

### Schedule translation

AWS cron differs from five-field cron in three ways the rewrite handles:

| cron | AWS | rule |
| --- | --- | --- |
| `0 2 * * *` | `cron(0 2 * * ? *)` | exactly one of day-of-month / day-of-week must be `?` |
| `0 5 1,15 * *` | `cron(0 5 1,15 * ? *)` | day-of-month restricted → day-of-week `?` |
| `30 1 * * 1-5` | `cron(30 1 ? * 2-6 *)` | AWS numbers days 1-7 with SUN=1; cron 0-6 (or 7) with SUN=0 |
| `0 4 * * 0,6` | `cron(0 4 ? * 1,7 *)` | lists are shifted element by element |
| `0 4 * * 5-7` | `cron(0 4 ? * 1,6,7 *)` | a range into cron's 7 (Sunday) wraps on AWS, so it becomes a list |
| `0 3 * * mon-fri` | `cron(0 3 ? * MON-FRI *)` | names pass through, uppercased |
| `@hourly` `@daily` `@weekly` `@monthly` `@yearly` | `cron(0 * * * ? *)` … `cron(0 0 1 1 ? *)` | expanded first (`@weekly` → `cron(0 0 ? * 1 *)`) |

Month names are uppercased; minute, hour, day-of-month and month values pass
through. The render fails (`backup-aws: …`) rather than run a different
schedule when:

- both day-of-month and day-of-week are restricted (`0 2 1 * 1`) — cron runs
  when EITHER matches, which AWS cannot express;
- the minute field is not a single value (`*/15 * * * *`, `0,30 * * * *`) —
  AWS Backup refuses jobs less than an hour apart;
- day-of-week uses a step (`1-5/2`), is out of range, or runs backwards;
- the expression is not five fields or an unknown shorthand (`@reboot`).

### Pausing

`paused: true` drops the `Selection`: AWS Backup has nothing left to back up,
while the vault, the plan and every recovery point stay (and still expire on
their own retention). `paused: false` composes it again.

Under `deletionPolicy: Orphan` a dropped MR would be orphaned in AWS — and an
orphaned selection keeps backing up. So when paused the Selection is first
re-rendered with `managementPolicies: ["*"]`, and dropped (and therefore
deleted in AWS) only once the observed object carries that policy: one extra
reconcile.

### Deleting

With `deletionPolicy: Delete` the selection, plan, role and attachments go
with the XR. The vault does not, while it holds recovery points: AWS refuses
to delete a non-empty vault and `forceDestroy` is deliberately never set, so
the `Vault` MR stays (deleting) until the recovery points expire or are
deleted by hand. With `Orphan` everything stays in AWS, including the
selection — backups continue under the orphaned plan.

### Ignored

AWS Backup protects the whole cluster, so the filters below can only make the
backup a superset of what was asked; they are ignored rather than failing the
render.

| field | why |
| --- | --- |
| `includedNamespaces`, `includedResources`, `excludedResources`, `labelSelector` | every namespace and resource type is backed up |
| `snapshotVolumes`, `defaultVolumesToFsBackup` | AWS Backup always protects the EBS/EFS/S3 storage behind the persistent volumes (CSI-provisioned only) |
| `destination` | recovery points go to the composed vault |
| `cluster.region`, `cluster.snapshotResourceGroup` | Azure-only; the region comes from the ARN |

Status written back to the XR:

| field | value |
| --- | --- |
| `provider` | `aws` |
| `ready` | every composed MR has `Ready=True` (the `Selection` only counts while it is composed) |
| `storageLocation` | the vault name (the XR name, known before anything reconciles) |
| `message` | the first non-Ready MR in composition order (vault, role, attachments, plan, selection): `<name> (<Kind>): <condition message, else reason>`, or `not created yet` |

AWS Backup reports no plan state, so there is no `phase`, `storageLocationPhase`
or `lastBackup`; backup jobs are visible with `aws backup list-backup-jobs
--by-resource-arn <cluster ARN>`.

## Prerequisites

Outside this XR, and required before a backup job can succeed:

- **EKS authentication mode `API` or `API_AND_CONFIG_MAP`.** AWS Backup reaches
  the cluster through an access entry; a `CONFIG_MAP`-only cluster cannot have
  one, and every job fails. The `cluster-aws` backend
  ([`../../cluster/aws/cluster.k`](../../cluster/aws/cluster.k)) does **not**
  set `accessConfig`, so its clusters get the EKS API default, `CONFIG_MAP`:
  switch them with `aws eks update-cluster-config --name <cluster>
  --access-config authenticationMode=API_AND_CONFIG_MAP` (a one-way change).
- **EKS opted in to AWS Backup in the region.** AWS Backup only protects
  resource types opted in through the region's settings
  (`resourceTypeOptInPreference`, e.g. the `RegionSettings` MR in
  provider-aws-backup, or the console's *Settings → Service opt-in*). That
  setting is account- and region-wide — one object per region, shared by every
  plan — so it is not composed per BackupPlan, where two plans would fight
  over it and deleting one would switch off the other.
- **Persistent volumes provisioned by the EBS/EFS/S3 CSI drivers** (EKS
  add-ons). In-tree and migrated volumes are not backed up.
- **Providers** `provider-aws-backup` and `provider-aws-iam`
  ([`../xrd/providers.yaml`](../xrd/providers.yaml)) and an AWS ProviderConfig
  with credentials for the cluster's account. No `providerConfigRef` is set,
  so the MRs use the provider's default (`ClusterProviderConfig` `default`).
  The credentials need IAM role/attachment and AWS Backup vault/plan/selection
  rights, plus `iam:PassRole` on the composed role (the Selection hands it to
  AWS Backup).
- **A KMS key policy** letting AWS Backup use `encryptionKmsKeyId`, when set.

`spec.cluster.id` must be the ARN. A `KubernetesCluster` XR on aws publishes
it as `status.id` once the cluster is observed (`status.name` is the bare
name, which is refused here).

## Usage

`main.k` reads `option("params")`, which `function-kcl` injects. Without it,
the package renders a built-in `_example` XR (namespace `default`, nightly at
02:00 UTC, cluster `arn:aws:eks:us-east-1:123456789012:cluster/example`). Pass
a real XR as `params.oxr`:

```bash
# built-in example: vault, role + attachments, plan, selection + status
kcl run packages/cloud/backup/aws

# the shipped example (weekdays 01:30 -> cron(30 1 ? * 2-6 *))
kcl run packages/cloud/backup/aws \
  -D params="{\"oxr\": $(yq -o json -I0 packages/cloud/backup/xrd/examples/backup-aws.yaml)}"
```

`ocds` takes observed composed resources keyed by composition-resource-name;
the status block reads each one's `Resource.status.conditions`, and the pause
logic reads `ocds.selection.Resource.spec.managementPolicies`.

Through Crossplane:

```bash
pnpm exec nx run backup-aws:render   # crossplane render of ../xrd/examples/backup-aws.yaml; needs docker
just install-module backup           # XRD + the Compositions, on the current cluster
```
