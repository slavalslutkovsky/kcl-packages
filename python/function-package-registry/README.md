# function-package-registry

The Crossplane composition function behind `packages/cloud/package-registry`:
it turns one `PackageRegistry` XR (`cloud.example.org/v1alpha1`) into the
registry resources of one backend, for OCI containers **and** language package
managers.

The Compositions are all the same two-step pipeline and differ only in the
function input:

```yaml
- step: render
  functionRef: {name: function-package-registry}
  input:
    apiVersion: packageregistry.fn.example.org/v1beta1
    kind: Input
    backend: gcp      # aws | gcp | azure | zot | forgejo
- step: ready
  functionRef: {name: function-auto-ready}
```

A `spec.formats` entry a backend cannot serve is a `SEVERITY_FATAL` function
result naming the format and the backends that do serve it — never a silently
dropped repository.

### helm

Charts are served as OCI artifacts wherever that is how the backend stores
them, and the `helm` endpoint is then the `oci://` reference `helm push` takes:

- **gcp** — a second DOCKER repository, `<xr name>-helm`.
- **azure**, **zot** — the same registry, under `<xr name>/charts` (zot is
  plain HTTP in-cluster: `helm push --plain-http`).
- **aws** — an ECR repository holds a single chart named after it, so helm
  composes a `RepositoryCreationTemplate` (CREATE_ON_PUSH, prefix
  `<xr name>/charts`): pushing `<chart>.tgz` to the endpoint makes ECR create
  `<xr name>/charts/<chart>` with the template's tag mutability, lifecycle
  and public-pull policy. Those repositories are ECR's, not the XR's — they
  survive the XR. A template applies a KMS key or tags only through an IAM
  creation role the XRD does not model, so `encryptionKeyId` with `helm` fails
  the render and tags are not applied to chart repositories.
- **forgejo** — Forgejo's native Helm chart repository: the endpoint is the
  `helm repo add` URL, published to with `helm cm-push` or a POST to
  `<endpoint>/api/charts`.

## Typed composed resources

Every managed resource this function composes is a **generated pydantic
model**, not a dict literal — the Python counterpart of the KCL schema
packages under `packages/providers/**` that `packages/cloud/**` renders
against.

`function/models/<provider>/` is generated by `just pkgreg-models` from the
CRDs of the same pinned provider images `packages/providers/registry.yaml`
lists, extracted the same way `just provider` extracts them (`docker create`
→ `docker export` → yq). They all inherit `function/models/base.py`:

```python
model_config = pydantic.ConfigDict(extra="forbid", validate_assignment=True)
```

so a misspelled field, a field set at the wrong nesting level, or a wrong type
is a `ValidationError` in `just pkgreg-test` instead of a key the API server
silently prunes at apply time. `resource.update()` serialises them with
`exclude_unset=True`, so the desired state contains exactly the fields a
renderer set — nothing defaulted, nothing null.

Chart values are the deliberate exception: `Release.spec.forProvider.values`
is `x-kubernetes-preserve-unknown-fields`, because a chart's value schema
belongs to the chart, not the provider. The XR `status` block is a plain dict
for the same reason the KCL renderers build theirs by hand — its schema is our
own XRD's.

## Development

```
just pkgreg-test                 # ruff + unit tests
just pkgreg-models               # regenerate function/models/** (docker + yq)
just pkgreg-serve                # serve :9443 for `crossplane render`
just pkgreg-render gcp           # render an example against the served function
just pkgreg-render aws-helm      # …or a per-format one (package-registry-aws-helm.yaml)
just pkgreg-image                # build the runtime image
just pkgreg-install              # image -> kind nodes, xpkg -> local registry
```
